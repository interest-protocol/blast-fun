Research date: 2026-10-26. Scope: first-party source research and a practical Blast architecture/migration recommendation. This document does not claim that the app-wide migration has been implemented or verified.

## What Uniswap actually does

| Source-supported fact | Useful principle for Blast |
| --- | --- |
| The monorepo separates standalone applications in `apps/`, shared code in `packages/`, and shared infrastructure/configuration in `config/`. It serves web, mobile and extension applications. [README](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/README.md), [architecture guidance](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/AGENTS.md#L60-L83). | Separate composition, domain behavior and generic controls. A folder/package boundary should reflect an actual ownership boundary. |
| `packages/ui` explicitly excludes app-specific and Uniswap business logic. Components should have reuse beyond one feature, hide implementation details and expose deliberate import paths; shared domain components belong in `packages/uniswap`. [UI philosophy](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/packages/ui/README.md#L5-L14). | A generic Button should know disabled/loading/focus semantics, but not wallet authentication, quote validity or transaction execution. |
| Theme modules define spacing, typography, color, icons, radii and z-index roles. Current Mycelium documents semantic surface/accent/status colors, typography, dark mode and shared animations. [Theme maps](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/packages/ui/src/theme/tokens.ts#L1-L79), [Mycelium](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/packages/mycelium/README.md#L15-L19). | Give each role one owner and let themes supply values. Keep brand selection distinct from success/loss/error. |
| Button has typed size, variant and emphasis options; it coordinates label, icon, spinner and unavailable activation. A deliberate `onDisabledPress` escape supports an explanation when an unavailable control remains interactive. Older root guidance and UI documentation still discuss Tamagui. Do not treat an older library recommendation as proof that every current surface uses that library. |
| Root lint restricts selected vendor and deep imports, directs list consumers through a shared wrapper, and prevents `ui` importing its own public barrel to avoid cycles. [Restrictions](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/oxlint.config.ts#L251-L272), [UI self-import rule](https://github.com/Uniswap/interface/blob/bdbace621994b658dcc4c7744f9181a8570d2a86/oxlint.config.ts#L1485-L1500). | Standards need an enforceable boundary, with implementation-only vendor access and explicit exceptions. |

## Blast's starting point

Blast already has the important foundation: npm workspaces, a framework-independent `packages/core`, Next routes, domain modules, shared `blast-ui` components, CSS tokens, a shared loader, skeletons, Sheet, inspection/copy affordances and library adapters. ESLint already enforces cross-package imports, TypeScript conventions and cognitive complexity; tests exercise those boundaries. Reuse that machinery. [Root scripts](../../package.json), [boundary configuration](../../eslint.config.mjs), [boundary tests](../../scripts/import-boundaries.test.mjs), [design rules](./BLAST-DESIGN-SYSTEM.md), [shared UI](../../apps/web/src/components/blast-ui/LoadingIndicator.tsx), [library adapter location](../../apps/web/src/components/ui-libraries/LibraryProviders.tsx).

The local new Button API already centralizes native activation, loading labels, unavailable states, sizes, variants and named icon buttons. TextField/SelectField/TextArea/FieldGroup and Checkbox establish additional owners. This is a suitable base to harden and extend. It is not sufficient evidence that all website controls now use it. [Button](../../apps/web/src/components/blast-ui/Button.tsx), [fields](../../apps/web/src/components/blast-ui/TextField.tsx), [checkbox](../../apps/web/src/components/blast-ui/Checkbox.tsx), [control styles](../../apps/web/src/components/blast-ui/Controls.module.css).

## Recommended Blast layering

These are recommendations, not descriptions of a completed refactor:

```text
app routes/layouts
  -> feature components/adapters: account, discovery, trade, presale, vesting, social
       -> shared visual components: Button, fields, Sheet, menu, tabs, feedback
            -> tokens + native elements / approved headless-library adapters

feature components/adapters -> domain modules -> framework-independent core / SDK
```

Keep generic web controls in the existing `apps/web/src/components/blast-ui` location. A new `packages/ui` is justified when another actual app needs the same React implementation; web and worker/bot consumers do not currently create that need. Keep `packages/core` free of React/Next. Keep business policies, queries, wallet operations and signed execution out of generic controls. A trade adapter computes `canSubmit` and handles review; Button displays that state and enforces its native interaction contract.

Prefer existing CSS Modules, semantic CSS variables, npm and ESLint. Uniswap's Bun/Nx/React Native/Tailwind migration solves its own multi-platform needs; adopting that stack is unnecessary for shared Blast controls. Use the existing headless libraries behind owned adapters for difficult focus/menu/dialog/select behavior. Preserve public semantic component props if the internal implementation changes.

Keep navigation as links. A single visual button recipe may style an owned link component, but replacing anchors with buttons would lose expected navigation behavior. Likewise, compound tabs, menu items, range/file inputs and third-party render-prop triggers may need owned implementations; the shared-control policy should cover their design and semantics rather than blindly rewrite every native tag.

## Standards and enforcement to add

1. **One control owner.** Sizes, radii, padding, typography, focus, pointer targets, icon geometry, loading, pressed, disabled and invalid states belong to shared controls. Feature classes own composition: grid placement, margin, width and alignment. If a repeated legitimate variant is missing, add it once with a clear name. Avoid page selectors that repaint shared internals.
2. **Semantic theme contract.** Global tokens own surface/ink/accent/status/focus roles. Scoped themes supply values, including the approved pink Blast workspace and any intentionally different launchpad theme. Controls should consume general semantic aliases rather than require a workspace ancestor. Keep raw color/geometry declarations confined to token/primitive owners and documented unavoidable chart/media geometry.
3. **Import boundaries.** Extend existing ESLint blocks so shared control modules cannot import feature modules, account stores, RPC/query clients or trading modules. Vendor control implementations are imported only by approved adapter modules. Reuse the existing static/dynamic/import-form tests. Avoid a broad barrel that accidentally pulls client code into server-only surfaces.
4. **Prevent new bypasses.** Add an AST-based check for new raw interactive elements outside shared owners and approved compound/adaptor files. Resolve aliases and wrappers where practical. Hidden security/file inputs, headless-library integration and special input types require specific entries, not a blanket directory exemption. A migration baseline records existing occurrences with file, element and reason; new entries fail CI and removed entries must be deleted. A raw-tag count alone is not a coverage metric.
5. **Guard styles without freezing layout.** Check new hardcoded colors and page overrides of shared-control visual properties. Use parsed declarations/selectors where feasible and a narrow audited legacy baseline. Do not ban legitimate data-driven chart dimensions or layout widths. Existing temporary `!important` control protection should have a removal condition: retire conflicting legacy selectors, then reduce specificity and verify the same contract.
6. **Behavior before appearance.** Shared tests cover native form type, disabled/busy activation, focusable unavailable explanations, icon accessible names, labels/errors, loading announcements, keyboard activation and ref/event composition. Financial integration checks still own quote freshness, precision, fee consent and submit/review. Test outcomes, not duplicated implementation constants.
7. **Visual acceptance across the app.** A test-owned control gallery covers all sizes/variants and long/missing labels, error/pending/disabled/selected states, light/dark, keyboard focus, touch, reduced motion and forced colors. Keep fixtures out of production imports/routes. Record actual browser geometry/contrast and screenshots; preserve the existing five-width and independent-review requirements in the design system. [Existing fixture boundary](../../apps/web/test/production-boundaries.test.ts).

## Staged migration across the whole website

| Stage | Work | Completion evidence |
| --- | --- | --- |
| 1. Inventory | Map route families and reusable controls: shell/Home, feed/posts/profiles, account/settings/notifications, discovery/workspace/portfolio, presales, vesting, competitions/invites, launchpad and operator surfaces. Include normal and rail/modal presentations. | Checked inventory names each control owner, legacy exception, route/state and verification status. No claim of app-wide completion from workspace screenshots. |
| 2. Harden shared controls | Establish semantic theme aliases, Button/IconButton, navigation action styling, fields, Checkbox, selection/tabs and existing overlay adapters. Keep new APIs small. | Focused semantic tests, control gallery, scoped lint/typechecks and measured visual acceptance. |
| 3. Adopt in vertical slices | Start with shell + account and one complete financial flow, then migrate remaining route families. Replace control and conflicting local style together. Preserve exact values, form behavior and state transitions. | Each migrated family removes its baseline entries and has ready/pending/error/empty plus relevant authenticated/unsupported-state evidence. |
| 4. Close the baseline | Review every remaining exception, including feature-owned semantic controls and external widgets; remove unused duplicate styles/components. | Zero unexplained bypasses, no growing exemptions, current route matrix and representative end-to-end verification. |
| 5. Maintain | Enforce boundaries in CI and require shared-component changes to name affected consumers and evidence. | New pages inherit the shared contract; intentional exceptions are explicit and reviewed. |

A realistic first implementation is the existing local primitive set, semantic token aliases, a finite bypass inventory and one complete migrated slice. It should establish the rules and demonstrate the result while leaving the remaining app-wide scope explicitly tracked. The website is complete only when that inventory closes with evidence.
